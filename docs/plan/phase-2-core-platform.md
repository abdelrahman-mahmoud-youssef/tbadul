Plan only. No code is written by this document. It is written against `main` at `c4fc30e` and the facts below were read on 2026-11-27.

Every statement carries one of four marks:

- `[repo]`: confirmed in this repository, with the path.
- `[docs]`: CONFIRMED in a primary source (official documentation, registry or the provider's own pages), with the URL, read 2026-11-27.
- `[proposal]`: a design choice of this plan. It can be challenged and nothing outside this document depends on it yet.

## 1. Scope

In scope: advertiser campaigns, performer tasks, the wallet and the double-entry ledger, the holding period with re-checks, strikes and withdrawal freezes, the API and web screens for all of it, minimal admin screens, and money in and out behind interfaces, last.

Out of scope: Telegram, Instagram, X and YouTube; share, view and save tasks; multi-currency; automated payouts beyond a stub; email or push notifications (status is shown in the app); referral programs; mobile apps.

Fixed by earlier work and not reopened here:

- A source failure is `source_error`, never `not_following`. A negative from one source is confirmed by the next. Daily budgets are per source. `[repo]` `docs/plan/phase-1-tiktok-verification.md` section 4.
- Money is `bigint` minor units with an ISO 4217 code, in an append-only double-entry ledger whose entries sum to zero per currency, enforced in the database. A task execution is unique per campaign and linked account. `[repo]` `docs/adr/0004-database-schema.md`, "Decisions for contexts not built yet".
- The contexts are Verification, Social Accounts, Campaigns, Tasks, Ledger, Payments and Trust and Safety. `[repo]` `docs/adr/0001-verification-context-architecture.md`, Context.

## 4. Contexts and packages

New packages, each with the layers of ADR 0001 (`domain`, `ports`, `application`, `adapters`, `testing`, a composition root, `index.ts`) and the boundary lint rules extended to them. `[proposal]`

```
packages/ledger      Ledger context: Money, accounts, journal entries, postings, balances, idempotency.
                     Knows nothing about campaigns, tasks or providers.
packages/exchange    Campaigns, Tasks, holds and re-checks, Trust. One package so that one transaction
                     can span reserve, complete, release and reverse. Sub-areas live in sub-folders of each
                     layer: src/domain/campaigns, src/domain/tasks, src/domain/holds, src/domain/trust, and
                     the same under ports, application, adapters, testing.
packages/payments    Payments context: PaymentGateway and PayoutGateway ports, the Paymob adapters, the
                     fake used by tests and by manual credit. Built last.
```

Dependencies: `exchange` imports the public surface of `ledger`, `verification` and `social-accounts`. `payments` imports `ledger`. `ledger` imports nothing of the others. `apps/web` still imports only `contracts`. `[proposal]`

### 4.1 One transaction across contexts

Every use case that moves money must change its state row and post its ledger entry in one Postgres transaction, or a crash between the two creates or loses money. The repository pattern in the repo takes a `Database` per adapter `[repo]`; the plan extends it with a unit of work. `[proposal]`

- `exchange/ports` defines, per sub-area, a unit of work: `run(work)` hands `work` a scope holding that sub-area's repositories and a `Ledger` port, all bound to one transaction.
- The Drizzle adapter opens `db.transaction(...)` and builds the scope from the transaction handle. `ledger` exports `drizzleLedger(executor)` so it can be built on a transaction handle as well as on the pool.
- No network call happens inside a transaction that holds locks. A use case reads what it needs, calls sources outside any transaction, then opens the transaction to write the result (section 9).

Triggers on `ledger_postings` (custom migration, hand-written SQL, as migrations 0001 and 0005 are `[repo]`):

1. **Balance projection**, `AFTER INSERT ... FOR EACH ROW`: `UPDATE ledger_accounts SET balance = balance + NEW.amount WHERE id = NEW.account_id AND tracked`. The row update takes the account's row lock, so concurrent postings to one account queue, and the nonnegative check refuses the one that would overdraw. `[proposal]`
2. **Zero-sum**, a constraint trigger `DEFERRABLE INITIALLY DEFERRED`, `AFTER INSERT ... FOR EACH ROW`: at commit, `sum(amount) group by currency` for `NEW.entry_id` must be 0, otherwise it raises. PostgreSQL documents constraint triggers as `AFTER ROW` triggers that can fire at the end of the transaction `[docs]` (https://www.postgresql.org/docs/current/sql-createtrigger.html). Because it is deferred, all postings of an entry may be inserted in any order. `[proposal]`

`tracked` accounts are the ones that carry a balance and the nonnegative check: `user_wallet`, `user_pending`, `campaign_escrow`, `payout_in_flight`. System accounts (`platform_revenue`, `provider_clearing`, `promo_pool`) are untracked: every release credits revenue, and a tracked revenue row would serialize all releases on one row lock. Their balance is a `sum(amount)` report. `[proposal]`

Sign convention: a posting's `amount` is the change in that account's balance. An entry sums to zero, so the sum of every account is zero at all times. That is a global invariant the reconciliation job checks (section 15, O1): the `-provider_clearing` balance equals everything users and campaigns hold plus platform revenue.

Posting order: a use case inserts an entry's postings sorted by `account_id`, so two transactions touching the same pair of accounts take the row locks in the same order and cannot deadlock. `[proposal]`

## 6. State machines

Every transition below is one transaction. A state change is a compare-and-set on `version` (or on the old state), so two actors racing for the same row cannot both win. `[proposal]` Where a transition writes to the ledger, the entry's idempotency key is derived from the object that changes state (section 7), so a retry after a crash finds the entry already posted and returns the stored result. Times come from the injected `Clock` passed to SQL as a parameter, as the claim repository does `[repo]`, so tests drive time with the manual clock.

`cancelled` and `completed` are terminal. Every other state has an exit that does not depend on a person: `ends_at` moves `active`, `paused` and `suspended` to `cancelling`; `cancelling` ends when its last reservation and hold resolve, and both resolve by themselves (reservations expire, holds release or reverse by the cap of section 10.5).

### 6.2 Reservation

| From       | To          | Triggered by                                                        | Preconditions                                                             | Written in the same transaction                                                                                                                                                                              |
| ---------- | ----------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| none       | `reserved`  | Performer, reserve                                                  | Eligibility of section 9.1                                                | `slots_taken + 1` on the target (conditional), the reservation with `expires_at = now + RESERVATION_TTL_MINUTES`. No ledger entry.                                                                           |
| `reserved` | `reserved`  | Performer, submit, answer `not_following`, `private` or `not_found` | State `reserved` and `expires_at` in the future; `next_submit_at` reached | A `task_checks` row; `next_submit_at` advanced by the cooldown schedule `[repo]` (`domain/cooldown.ts` in `social-accounts`). A `source_error` writes no `task_checks` row and answers `source_unavailable`. |
| `reserved` | `held`      | Performer, submit, answer `verified`                                | As above; for a like, `likes_visible`; for a comment, the rules pass      | Reservation state; the hold (section 6.3) with its planned check times; ledger `complete:{reservationId}`; a `task_checks` row with purpose `submit`.                                                        |
| `reserved` | `expired`   | System, at `expires_at`                                             | `expires_at` reached                                                      | `slots_taken - 1`. Done by the sweeper and lazily by the next reserve on the same target.                                                                                                                    |
| `reserved` | `cancelled` | Performer, cancel                                                   | State `reserved`                                                          | `slots_taken - 1`.                                                                                                                                                                                           |

`expired`, `cancelled`, `released` and `reversed` are terminal. A reservation always leaves `reserved` by the TTL, so a slot cannot stay taken forever.

### 6.3 Hold

| From      | To         | Triggered by                                                                                                               | Preconditions and rule                                                                                              | Written in the same transaction                                                                                                                                                                                        |
| --------- | ---------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| none      | `holding`  | Completion (section 6.2)                                                                                                   | `ends_at = starts_at + HOLD_PERIOD_HOURS`; `planned_checks` drawn at random inside the period (section 10.2)        | The hold row, with reward and fee copied from the target.                                                                                                                                                              |
| `holding` | `holding`  | Re-check, answer `verified`                                                                                                | Check is due                                                                                                        | `task_checks`, `checks_done + 1`, `next_check_at` set to the next planned time or to `ends_at`.                                                                                                                        |
| `holding` | `holding`  | Re-check, answer `private`                                                                                                 | The list or likes are hidden, or the account is private. Not a violation.                                           | `task_checks`, `blocked_reason = 'private'`, `extended_until` pushed out by `EXTENSION_STEP_HOURS` up to `MAX_HOLD_EXTENSION_DAYS`, `next_check_at` set to retry later. `released` and `reversed` are terminal and mutually exclusive: both transitions are a compare-and-set on `state = 'holding'`, so exactly one commits. The three ways a hold can stall (hidden list, source outage, never-exhausted list) each have a cap that forces a decision (section 10.5), so no hold waits forever.

### 6.4 Payout (stub until P1)

`requested` to `settled` or `failed`. A request moves the money out of the wallet at once, so it cannot be spent twice; a settlement or a failure moves it on. A `requested` payout older than a limit is inquired by its `client_reference` and forced to a terminal state (P1). See 7.2 for the entries.

### 6.5 Withdrawal freeze

Created by the strike rule (section 13) or an admin; lifted by an admin. At most one active freeze per user is a database rule. A payout request in a transaction that finds an active freeze is refused with `withdrawals_frozen`.

## 7. Money

### 7.1 Accounts and the unit price

- A person's wallet is `user_wallet` (spendable and withdrawable). Rewards in holding sit in `user_pending`. A campaign's money sits in `campaign_escrow`. `payout_in_flight` holds money requested for payout and not yet settled. `platform_revenue`, `provider_clearing` (one per provider, plus `manual`) and `promo_pool` are system accounts. `[proposal]`
- A target has a **reward** `r` (paid to the performer) and a **fee** `f` (kept by the platform), both integers in minor units, fixed when the campaign is created from the fee rule of section 14 and never recomputed. The **unit price** is `p = r + f`. A campaign's budget is `B = sum over targets of slots_total * p`.
- Worked example used below: `r = 500`, `f = 100` (5.00 and 1.00 EGP), so `p = 600`; a campaign of 100 follow slots has `B = 60,000`.

### 7.2 Entries

Every entry has a unique idempotency key derived from the object that changes state. Postings are signed (positive credits the account). Each entry sums to zero.

| Flow                                | Idempotency key              | Postings                                                                                                        | Guards                                                                                                                                                                                                                                                                                                                                      |
| ----------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Top-up (P1)                         | `topup:{paymentIntentId}`    | `provider_clearing(paymob_accept) -A`, `user_wallet(u) +A`                                                      | Intent moves `created` to `paid` by compare-and-set only after the callback HMAC and a server-side inquiry agree (section 10.8).                                                                                                                                                                                                            |
| Manual credit before P1             | `adjust:{uuid}`              | `provider_clearing(manual) -A`, `user_wallet(u) +A`                                                             | Admin with 2FA, memo required, `actor_user_id` recorded.                                                                                                                                                                                                                                                                                    |
| Fund a campaign                     | `fund:{campaignId}`          | `user_wallet(adv) -B`, `campaign_escrow(c) +B`                                                                  | Nonnegative check on the wallet; campaign `draft` to `active` by compare-and-set in the same transaction.                                                                                                                                                                                                                                   |
| Reserve a slot                      | none                         | none                                                                                                            | The money for the slot is already in escrow as part of `B`. Only `slots_taken` changes.                                                                                                                                                                                                                                                     |
| Complete a task                     | `complete:{reservationId}`   | `campaign_escrow(c) -r`, `user_pending(u) +r` (omitted when `r = 0`)                                            | Reservation `reserved` to `held` by compare-and-set; escrow must hold `r` (nonnegative check).                                                                                                                                                                                                                                              |

| Close the campaign                  | `sweep:{campaignId}`         | `campaign_escrow(c) -R`, `user_wallet(adv) +R`, where `R` is the escrow balance                                 | Posted once when a `cancelling` campaign has no open reservation or hold (the residue is refilled slots and expired reservations), and for `completed` when `R > 0`.                                                                                                                                                                        |
| Payout request (P1)                 | `payout_request:{payoutId}`  | `user_wallet(u) -X`, `payout_in_flight +X`                                                                      | Nonnegative check; no active freeze; unique `client_reference`.                                                                                                                                                                                                                                                                             |

| Provider fee (reconciliation)       | `provider_fee:{reference}`   | `platform_revenue -x`, `provider_clearing +x`                                                                   | Posted by the reconciliation job, never by a user path.                                                                                                                                                                                                                                                                                     |

Worked example (`r = 500`, `f = 100`, 100 slots): funding posts `wallet -60,000`, `escrow +60,000`. One task completes: `escrow -500`, `pending +500`, escrow 59,500. If it releases: `pending -500`, `wallet +500`, `escrow -100`, `revenue +100`, escrow 59,400. If instead it reverses: `pending -500`, `escrow +500`, escrow back to 60,000 and the slot is open again.

### 7.3 Invariants

The reconciliation job (O1) checks these on a schedule and writes the result to `invariant_runs`; the first two and the zero-sum rule are also database rules.

| Id  | Invariant                                                                                                                                                                                                                                                                                                                                                                                                           | Where it is held                     |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| I-1 | The sum of every posting is zero; equivalently the sum of all account balances is zero.                                                                                                                                                                                                                                                                                                                             | Database (per entry), job (global)   |
| I-2 | No tracked account balance is negative.                                                                                                                                                                                                                                                                                                                                                                             | Database                             |
| I-3 | For a campaign in `active`, `paused` or `suspended`: escrow equals `sum over targets of (p * (slots_total - slots_taken) + p * reserved + f * holding)`, counting that target's reservations in `reserved` and holds in `holding`. For `cancelling`: escrow is at least `sum of (p * reserved + f * holding)`, the excess being refilled slots awaiting the sweep. For `cancelled` and `completed`: escrow is zero. | Job                                  |
| I-4 | For a user, `user_pending` equals the sum of `reward_minor` of that user's holds in `holding`.                                                                                                                                                                                                                                                                                                                      | Job                                  |
| I-5 | `slots_taken` of a target equals the count of its reservations in `reserved`, `held` or `released`.                                                                                                                                                                                                                                                                                                                 | Job (the bounds are a database rule) |
| I-6 | Each `released` hold has exactly one `complete` and one `release` entry; each `reversed` hold has exactly one `complete` and one `reverse` entry; no hold has both a release and a reverse entry.                                                                                                                                                                                                                   | Job                                  |
| I-7 | The money that entered through providers minus settled payouts equals the negated `provider_clearing` balances.                                                                                                                                                                                                                                                                                                     | Job                                  |

Check against the example: with one task held, `p * (100 - 1) + f * 1 = 59,400 + 100 = 59,500`, which is the escrow after completion.

### 7.4 No clawback after the hold

After release the reward is in the wallet. A violation found later by a spot check is a strike and may freeze withdrawals; it does not claw money back. The alternative, letting a wallet go negative as tfa3al does (it deducts the amount "possibly into negative balance" `[docs]`, https://tfa3al.com/terms, section 10.5), would break I-2 and every statement that relies on it, so it is rejected for the MVP. A deduction from the remaining wallet balance (never below zero) is a possible later rule and a client decision (D6).

## 9. Task distribution

### 9.1 Who can reserve what

All of these must hold. The ones marked "database" are also refused by the database if the application is wrong.

1. The caller has an active linked account on the target's platform, and names which one performs. `[repo]` (`linked_accounts`)
2. The campaign is `active` and the target has an open slot. (database: `campaign_targets_slots_bounds`)
3. The target is not the performer's own: the advertiser is not the caller, and the target account is not one of the caller's linked platform accounts. `[proposal]`
4. The caller has no live reservation for the target. (database: `reservations_one_per_user_target`)
5. For a follow, the performer's following list is visible; for a like, `likes_visible` is true. `[repo]`
6. **Baseline: the performer does not already follow the target (or already like the video).** One `verifyFollowsBatch` for the candidates read from the performer's list answers it, and the verifier's 30 s list cache absorbs repeats `[repo]`. `verified` means "already does it": the pair is recorded in `task_exclusions` and the answer is `already_following`. `not_following` lets the reservation go ahead. `private` or `not_found` is `not_eligible`. A `source_error` reserves nothing and answers `source_unavailable`. The check runs at reserve time, never when the feed renders, so browsing costs nothing. `[proposal]`
7. Caps: open reservations per user at most `MAX_OPEN_RESERVATIONS_PER_USER`, completed tasks per linked account per day at most `DAILY_TASK_CAP_PER_ACCOUNT`, and a throttle while the user's reversal rate is above `REVERSAL_THROTTLE_RATE`. `[proposal]`
8. The user is not banned (`auth_users.banned` exists `[repo]`).

`task_exclusions` is a small table: `(target_id, platform_account_id)` unique, `reason`, `at`. It stops the same account paying for the same baseline twice. `[proposal]`

### 9.2 Fairness and the feed

The feed is a cursor-paged list of open targets the caller may reserve (rules 1 to 5 and 8 are evaluated in SQL; rule 6 is not, because it costs a source call). Order: lowest fill ratio first, then a stable per-performer pseudo-random tie-break from `hash(user_id, target_id, day)`, then newest. The tie-break stops every performer from landing on the same first row, which is also what keeps one hot target row from becoming the bottleneck. `[proposal]`

### 9.3 Reserve, step by step

1. Outside any transaction: evaluate the baseline of 9.1 rule 6. No lock is held during the network call.
2. One transaction:
   1. Take `pg_advisory_xact_lock(hashtextextended(user_id || ':reserve', 0))`, the claim repository's pattern `[repo]`.
   2. Count the user's `reserved` reservations; refuse at the cap with `reservation_limit_reached`.
   3. Expire this target's overdue reservations (`reserved` with `expires_at` passed) and give their slots back in the same statement.
   4. Take the slot: `UPDATE campaign_targets SET slots_taken = slots_taken + 1 WHERE id = $1 AND slots_taken < slots_total AND <the campaign is active> RETURNING ...`. Zero rows means the target is full or closed: `target_full`.
   5. Insert the reservation. A violation of `reservations_one_per_user_target` becomes `already_reserved`.
3. Commit. No ledger entry: the budget already covers the slot.

A hot target serializes only its own takers on one row update. That is hundreds of reservations a second, far above the expected load; if one target ever needs more, its counter can be split across several rows. `[proposal]`

### 9.4 Concurrency

| Situation                                                        | What prevents the wrong outcome                                                                                                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Two performers take the last slot                                | The conditional `UPDATE ... WHERE slots_taken < slots_total`: one updates a row, the other updates none. The check constraint is the backstop.                                                                                                                                                                                                                                                |
| One person reserves the same target twice                        | `reservations_one_per_user_target`.                                                                                                                                                                                                                                                                                                                                                           |
| A person double-clicks submit                                    | Compare-and-set `reserved` to `held`; the second finds the reservation no longer `reserved`. The ledger key `complete:{reservationId}` would refuse a second posting anyway.                                                                                                                                                                                                                  |
| Release and reversal race (the gate and an advertiser rejection) | Both are compare-and-set on `holds.state = 'holding'`; one commits, the other changes nothing and reads the winner's state.                                                                                                                                                                                                                                                                   |
| Expiry sweeper races a submit                                    | Submit requires `state = 'reserved'` and `expires_at` in the future in the same statement as its update; the sweeper requires `expires_at` passed. Whichever updates the row first wins. Two sweepers do not clash because they take rows with `FOR UPDATE SKIP LOCKED`, which PostgreSQL documents for queue-like tables `[docs]` (https://www.postgresql.org/docs/current/sql-select.html). |
| Fund twice, or fund while a withdrawal drains the wallet         | Unique `fund:{campaignId}`; the wallet's nonnegative check and its row lock make the second debit fail cleanly.                                                                                                                                                                                                                                                                               |
| Advertiser cancels while performers submit                       | Lock order is fixed: user advisory lock, then campaign row, then target rows, then reservation or hold rows, then ledger accounts by ascending id. A submit that loses the campaign lock re-reads the state and finds `cancelling`.                                                                                                                                                           |
| A retry after a crash                                            | Every money transition is one transaction with a deterministic idempotency key: the retry finds the key and returns the stored entry.                                                                                                                                                                                                                                                         |

Isolation stays at the default `READ COMMITTED` with explicit conditional updates and row locks; no `SERIALIZABLE` retry loop is needed. Drizzle accepts `isolationLevel` per transaction `[docs]` (https://orm.drizzle.team/docs/transactions) if a case ever needs it. Row locks in the select builder are available in the installed `drizzle-orm` 0.45.4 as `.for('update', { skipLocked: true })` `[repo]` (`node_modules/drizzle-orm/pg-core/query-builders/select.d.ts`, line 586, and `select.types.d.ts`); the official docs pages read do not mention them, so the first slice that uses them proves them with a test.

### 9.5 Reservation expiry

A minute-interval tick (section 10.1) runs one statement: select up to 500 overdue `reserved` rows `FOR UPDATE SKIP LOCKED`, mark them `expired`, and decrement each target's `slots_taken` by the number expired. The lazy expiry in 9.3 keeps a slot from staying blocked between ticks. `[proposal]`

### 9.6 Submitting, and comment tasks

Submitting reuses the claim flow: a cooldown after each failed attempt, a per-user rate limit (`@RateLimited('submit-task')`), and a `source_error` that records nothing and answers `source_unavailable` `[repo]` (`verify-account-claim.ts`, `claims.controller.ts`). A comment task adds the text the performer posted. Rules: minimum length, normalization (Unicode NFKC, lower case, collapsed whitespace) into `text_fingerprint`, and the unique index refuses the same text twice on one target. An advertiser may reject a comment during its hold with a reason from a closed list (`spam_or_off_topic`, `duplicate`, `abusive`); a rejection is a reversal with reason `advertiser_rejected`, limited to `ADVERTISER_REJECT_SHARE` of a target's slots without an admin, and the rejection rate of each advertiser is on the admin ops screen. `[proposal]`

## 10. The re-check engine

### 10.1 The database is the schedule, the queue is the executor

`holds.next_check_at` and `holds.planned_checks` are the schedule. A queue only triggers work, so losing it loses nothing and a duplicated job is harmless. `[proposal]`

- A cron tick every minute selects due work: holds with `next_check_at` reached (grouped by performer account), overdue reservations (section 9.5), and holds past `ends_at` awaiting their gate.
- For each performer account it enqueues one job with `singletonKey = performer account id`, so at most one job per performer is pending, and a random `startAfter` inside `RECHECK_SPREAD_MINUTES` so re-checks do not arrive in peaks. This is the spreading rule already written for the traffic governor `[repo]` (`docs/plan/phase-1-tiktok-verification.md` section 15.6, "Re-check spreading").
- The handlers (`recheckPerformer`, `sweepReservations`, `releaseDueHolds`) are plain use cases that take the `Clock`. The queue calls them; tests call them directly with the manual clock. No test waits for a real timer.

### 10.2 Scheduling inside the hold

At completion the hold draws `RECHECKS_PER_HOLD` random instants inside the period, at least `RECHECK_MIN_GAP_HOURS` apart and not later than the last gap before `ends_at`, then adds the gate at `ends_at`. The draw is skewed early: a following list is newest first, so a target is cheapest to find soon after the follow and dearest a week later (10.4). Random times mean a performer cannot know when to follow again. `[proposal]`

### 10.3 Batching per performer

One read of a performer's list answers every task of that performer for that platform. When a performer's job runs it takes all of that performer's `holding` holds with `next_check_at` within `RECHECK_BATCH_WINDOW_HOURS`, pulls them forward, and makes one call per check kind: a single `verifyFollowsBatch` with every followed target `[repo]`, and one liked read per kind of like target (comments wait for requirement V4). Reads therefore scale with performers and windows, not with tasks times checks. `[proposal]`

### 10.4 Reading to the end, or not reversing

Following and liked lists come back newest first. A performer who follows many accounts after the task pushes the target past the page cap, and the chain then answers `not_following` with `listExhausted = false`. The repo already records this hazard for the `watch` command: a target that moves past the cap reads as an unfollow unless a confirming source settles it `[repo]` (phase-1 plan section 7, `watch follows`). At submit time that answer is fine, because the performer just acted. At re-check time it would reverse an honest performer's money. Rules: `[proposal]`

1. A re-check always passes the performer's `performerFollowingCount` from a fresh profile (cached by the profile cache `[repo]`). The chain's short-list rule then turns a `not_following` read from a list shorter than that count into `source_error` with kind `incomplete_list`, so it falls through to the next source `[repo]`.
2. **A reversal needs `listExhausted = true` in the verdict's evidence** (the field exists in `ListEvidence` `[repo]`), plus the chain's own confirmation by a second source. Anything else is stored as `inconclusive` and reverses nothing.
3. An `inconclusive` read is retried with a deeper read up to `RECHECK_MAX_PAGES`. That needs a per-call page cap, which the verifier takes from its config today (`pageCap` is fixed in `apps/api/src/core/compose.ts` `[repo]`): requirement V2.
4. A list still not read to its end at the gate follows section 10.5.

Cost, computed and not measured. Tokapi PRO is priced at $12.99 for 1,500,000 requests a month at 180 a minute `[repo]` (phase-1 plan fact 93), about $0.0000087 a request, so money is not the constraint; the rate limit and the daily caps are. Assume 10,000 holds a day, each with 2 random checks and a gate, and that three of a performer's holds fall in one batching window: about 10,000 list reads a day. At an average of 3 pages that is 30,000 requests a day, 900,000 a month, 12 % of the per-minute capacity and 60 % of the monthly plan. Without batching the same load is 30,000 reads, 2.7 million requests a month, which exceeds that plan. Batching and early, shallow checks are therefore load-bearing. The depth distribution is the first number to measure, with the ramp test of phase-1 section 15.7. Likes cost more: the liked order is `scraper, ensemble` only, with 1 EnsembleData unit per liked-posts call `[repo]` (ADR 0003; phase-1 plan section 14).

### 10.5 What happens when a check cannot be completed

| Situation during the hold                               | Outcome                                                                                                                                                                                                                                                                                                     | Strike                                   |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Following list hidden, likes hidden, or account private | Not a violation. `blocked_reason = 'private'`, the hold is extended a step at a time up to `MAX_HOLD_EXTENSION_DAYS`, the performer is told to make it public. After the cap: reversed with `unverifiable`.                                                                                                 | No                                       |
| Account no longer exists (`not_found`)                  | Reversed with `account_gone`.                                                                                                                                                                                                                                                                               | No                                       |
| `not_following` confirmed, list read to its end         | Reversed with `unfollowed` (or `unliked`, `comment_removed`).                                                                                                                                                                                                                                               | No (counts toward the reversal throttle) |
| Source outage or the background budget share spent      | The hold waits with backoff. After `MAX_HOLD_EXTENSION_DAYS` past `ends_at`: with `OUTAGE_RELEASE_POLICY = release` and at least one conclusive `verified` in the hold (the submit counts), release with `resolution_reason = 'unverified_cap'` and queue a priority spot check; with `hold`, keep waiting. | No                                       |
| List not read to its end at the gate                    | Deeper read up to `RECHECK_MAX_PAGES`; then as the outage row.                                                                                                                                                                                                                                              | No                                       |

The outage row is client decision D5: paying on the benefit of the doubt after an outage of our own, against holding an honest performer's money for as long as the providers are down. The recommendation is `release`, because an outage on our side should not be paid for by performers, and the spot check recovers the rest. A source error is never read as a negative in any row, which is the verification rule `[repo]`.

After release, a **spot check** runs with probability `SPOT_CHECK_RATE` within `SPOT_CHECK_WINDOW_DAYS`. A confirmed violation (`unfollowed_after_hold`, `unliked_after_hold`, `comment_removed_after_hold`) writes a `task_checks` row and a strike.

### 10.6 Budgets, priority and where the runner lives

- Source budgets are counted in memory per process, seeded from `verification_checks` at the start of each UTC day `[repo]` (`with-budget.ts`), and have no notion of priority.
- A user's verify must never wait behind background work, and a re-check that finds no capacity is rescheduled, not failed `[repo]` (phase-1 plan section 15.5). A **background budget share** enforces it: a performer job calls sources only while the first paid source of the relevant order has spent less than `RECHECK_BUDGET_SHARE` of its daily budget (default one half). The honest place for this is the verifier, as a priority class on the call that withholds that share from background calls (requirement V3). Until it exists, the composition computes the share from `SpendLedger.spentSince` and defers.
- Because the counters are per process (ADR 0005, "A second API process ... shares the daily budget only through the seed read at the start of each day" `[repo]`), **the queue workers run in the API process, with one replica**, so re-checks and users draw on the same counters. Scaling out first needs a shared counter. Worker concurrency stays small (`QUEUE_LOCAL_CONCURRENCY`, default 2) so background work cannot fill the verifier's per-source bulkhead, whose default is 4 calls and a queue of 32 `[repo]` (`VERIFICATION_CONCURRENCY`, `VERIFICATION_QUEUE`).

### 10.7 Job runner: evaluation and recommendation

| Option                                             | Infrastructure added                                                                         | Enqueue in the same transaction as the write                                                                                            | Scheduling, delay, dedupe                                                                                                                                        | Fit                                                                                                                                                           |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **pg-boss** 12.40.0                                | None: it uses the Postgres the repo already runs                                             | Yes: `send(name, data, { db })` runs the insert in the caller's transaction through an adapter; a `fromDrizzle` adapter exists `[docs]` | `startAfter`, `singletonKey`, `singletonSeconds`, retry limit, delay and backoff, `schedule` with cron, `work` with `localConcurrency`, graceful `stop` `[docs]` | Best. The schedule already lives in Postgres; money state and enqueue can commit together.                                                                    |
| BullMQ 6.7.10 on Redis                             | A Redis service, with `maxmemory-policy noeviction` and persistence (AOF preferred) `[docs]` | No: Redis cannot join a Postgres transaction, so an outbox table and a dispatcher would be needed                                       | Delayed jobs, job schedulers, rate limiting, flows                                                                                                               | Higher throughput and more features than this load needs, for one more stateful service to run, back up and pay for on Railway.                               |
| BullMQ on its Postgres backend                     | None                                                                                         | Not documented                                                                                                                          | Same API as the Redis backend                                                                                                                                    | BullMQ's own guide calls the Redis backend "the default and the most battle-tested", so the optional Postgres backend is the less proven of the two `[docs]`. |
| A hand-written table with `FOR UPDATE SKIP LOCKED` | None                                                                                         | Yes                                                                                                                                     | Retries, backoff, cron, graceful stop all hand-written                                                                                                           | Rejected: the repo's rule is to look for a mature maintained package before writing a capability.                                                             |

**Recommendation: pg-boss.** It needs Node 22.12 or higher and PostgreSQL 13 or higher `[docs]`; the repo pins Node 26 and PostgreSQL 18 `[repo]`. It adds no service, it lets enqueue commit with the state change, and the design above does not need more than it offers. The trade-off is a throughput ceiling and table churn on the one database the money lives in, and a second schema (`pgboss`) that the library migrates itself, against the repo's rule that migrations are generated by drizzle-kit and reviewed `[repo]` (ADR 0004). The expected volume (tens of thousands of jobs a day, one per performer window) is well inside what a Postgres queue handles. To contain the schema point, the library's schema migration runs in the same deploy step as `pnpm --filter @engagement-exchange/db migrate`, not at an arbitrary application start. The design isolates the choice: the queue sits behind a three-method port (`enqueue`, `work`, `schedule`), so BullMQ could replace it without touching the use cases.

Two things are not yet proven and are checked by a spike in slice S5 before anything depends on them: that `fromDrizzle` works with the repo's `drizzle-orm/node-postgres` driver (the documented example uses the Bun driver), UNCONFIRMED; and that `drizzle-kit` ignores a schema it does not define, so it will not try to drop the `pgboss` tables, UNCONFIRMED. If the first fails, enqueue goes through a small outbox table drained by the tick; the schedule is already in the database, so nothing else changes.

### 10.8 Money in and out (Payments, last)

Everything here is behind two ports, `PaymentGateway` (create a checkout, verify a callback, inquire) and `PayoutGateway` (send, inquire). Facts read from Paymob's own pages on 2026-11-27:

- **Top-up.** A checkout is created by `POST https://accept.paymob.com/v1/intention/` with `Authorization: Token <secret key>`; the amount is in cents; `special_reference` carries a merchant reference returned in the callback as `merchant_order_id`; `notification_url` and `redirection_url` are request fields. No idempotency key or duplicate-request behaviour is documented. `[docs]` https://developers.paymob.com/paymob-docs/intention-apis/create-intention.md. So double crediting is prevented on our side: `payment_intents.special_reference` is unique and `created` to `paid` is a compare-and-set that posts `topup:{id}`.
- **Callback.** The transaction callback carries an HMAC, HMAC-SHA512 over a fixed list of 20 fields concatenated in lexicographic order, keyed with the account's HMAC secret. `[docs]` https://developers.paymob.com/paymob-docs/developers/webhook-callbacks-and-hmac/hmac/hmac-transaction-callback. A callback is believed only after the HMAC matches and a server-side inquiry by transaction id agrees (`GET api/acceptance/transactions/{id}`, `[docs]` https://developers.paymob.com/paymob-docs/transaction-inquiry-apis/transaction-inquiry/by-transaction-id.md). Refund and void exist (`[docs]` https://developers.paymob.com/paymob-docs/manage-payment-apis/refund.md).
- **Payouts.** They are paid from a pre-funded payout budget that is separate from the collection balance and is topped up by bank transfer or an internal transfer; a payout over the budget is declined. `[docs]` https://developers.paymob.com/paymob-docs/beyond-payments/payouts/how-it-works-1.md. Channels in Egypt: Vodafone Cash, Etisalat Cash, Orange Cash, Bank Wallet, Bank Card, Instant Bank and Egypt Post; wallet limits per recipient are 60,000 EGP per transaction and per day and 200,000 per month. `[docs]` https://developers.paymob.com/paymob-docs/beyond-payments/payouts/disbursement-channels.md. A single payout is `POST api/secure/disburse/` with a Bearer token from an OAuth password grant; `client_reference_id` is documented as a reconciliation aid, **not** as a deduplication key. `[docs]` https://developers.paymob.com/paymob-docs/payouts-apis/cashin-api/vodafone-cashin.md. Wallet payouts resolve immediately, bank and Egypt Post payouts asynchronously, and the documented callback covers bank transactions only. `[docs]` https://developers.paymob.com/paymob-docs/payouts-apis/payout-callbacks.md.
- **Consequences for the design.** `payouts.client_reference` is unique and a retry of a payout whose answer was lost inquires by that reference before it sends again (`GET /api/secure/transaction/inquire/`); the wallet is debited at request time, so a payout cannot be spent twice; the ledger keeps two clearing accounts for Paymob, `paymob_accept` for collections and `paymob_payout` for the payout budget, and an internal transfer entry moves money between them; a payout `requested` for longer than a limit is inquired and forced to a terminal state.
- **Onboarding.** There is no self-signup: Paymob provisions the account after a legal agreement, issues staging credentials, then approves production after a technical review. `[docs]` https://developers.paymob.com/paymob-docs/beyond-payments/payouts.md. Its integration checklist says the risk team assesses a merchant "based on business model and transaction activity" `[docs]` https://developers.paymob.com/paymob-docs/getting-started/integration-checklist.md. Which business types are eligible or prohibited, the KYC documents, the fees and the staging base URL are all UNCONFIRMED: the pages read do not say. Whether a paid-engagement marketplace will be accepted is therefore open (D3). tfa3al's own terms say gateway top-up is stopped and balances are sold through approved resellers `[docs]` (https://tfa3al.com/terms, section 13); the planned fallback is the same shape: a manual admin credit (section 7.2) and manual payout approval, which need only the ledger.

### 15.4 Working in a shared checkout

Several sessions share one working tree and one git index. The rules below keep their work from colliding. `[proposal]`

1. **One committer.** One session stages and commits; the others do not run `git add`, `commit`, `stash`, `checkout`, `reset` or any command that changes repository state. A slice session ends by listing the paths it changed, the scoped checks it ran and a one-line summary. The committer confirms that `git status` shows only declared paths, stages them by explicit path (never `git add -A`), runs the whole gate and the review pass of `.claude/skills/engineering-standards`, and commits one slice step at a time with a neutral conventional message and no comments in code `[repo]` (`CLAUDE.md`).
2. **Path ownership.** A session writes only the paths its slice owns (15.2). A change needed elsewhere is a request to the owner, kept in the repository's untracked working-notes location (see `CLAUDE.md`), never an edit.
3. **Interfaces first.** Ports and contracts land, and are committed, before the code that implements or consumes them. S0 and C1 exist for this.
4. **Migrations have one owner.** Only S1 touches `packages/db/drizzle`. The journal is one file and numbers are sequential `[repo]`, so two writers would collide. A migration that has been applied is never edited.
5. **Pushes to `main` deploy.** In the Railway project the `web` and `api` services use the GitHub repository's `main` branch as their source, so a push to `main` builds both; the signer is deployed by upload and does not follow pushes (Railway configuration read with the CLI on 2026-11-27; `web` redeployed within minutes of the push of a documentation-only commit). Neither service has watch paths yet, so every push rebuilds both. The API image applies migrations when it starts `[repo]` (`apps/api/Dockerfile`). So migrations are additive (new tables and nullable columns), a change that removes or tightens something is done in two steps, and every new behaviour sits behind `EXCHANGE_ENABLED`, off by default.
   Watch paths, derived from what each image builds (its Dockerfile copies the whole repository, installs the workspace, then builds the service and its workspace dependencies): the API watches `/apps/api/**` and the packages it depends on, `contracts`, `db`, `social-accounts` and `verification`; the web app watches `/apps/web/**` and `contracts`; both also watch `/package.json`, `/pnpm-lock.yaml`, `/pnpm-workspace.yaml`, `/tsconfig.base.json` and `/.dockerignore`. Railway's patterns are gitignore-style and anchored at the repository root with a leading slash `[docs]` (https://docs.railway.com/builds/build-configuration, read 2026-11-27); exclusion patterns are UNCONFIRMED and not used. When `ledger`, `exchange` or `payments` become dependencies of the API (S0 onward), their folders are added to the API's list in the same change.
6. **Scoped commands only.** Slice sessions run `pnpm --filter <package> lint typecheck test`, and format only the paths they own (`pnpm exec prettier --write <paths>`), never `pnpm format` or a repository-wide write, which would rewrite another session's unsaved files. The full `pnpm lint`, `typecheck`, `test` and `build` are for the committer. Dependencies are installed once, by S0; slice sessions do not touch `pnpm-lock.yaml`.
7. **One database-test suite at a time.** Each package's database tests start their own container `[repo]`. The machine runs Docker for every session and has limited disk and memory, so a session announces before it runs a suite and no two run together.
8. **Shared files.** Each has one owner and a rule.

| File                                                                                                        | Owner                     | Rule                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `eslint.config.js`, `knip.json`, `pnpm-workspace.yaml`, `pnpm-lock.yaml`, root `package.json`, `turbo.json` | S0                        | Changed by S0, or by the committer on request.                                                                                                                                                                                                                                                               |
| `packages/db/src/schema/**`, `packages/db/drizzle/**`                                                       | S1                        | Requests only.                                                                                                                                                                                                                                                                                               |
| `packages/contracts/src/{index,vocabulary,errors}.ts`                                                       | S0, then C1               | Error codes only in S0.                                                                                                                                                                                                                                                                                      |
| `apps/api/src/{app.module.ts,core/*,http/errors.ts}`                                                        | S0                        | Slices fill their own `core/compose-<area>.ts` and their own module folder.                                                                                                                                                                                                                                  |
| `apps/web/messages/ar.json`                                                                                 | S0 creates the namespaces | Each web slice edits only its own top-level block with small edits, re-reads the file first, never reformats the file. If concurrent edits prove unsafe, the file is split per namespace and merged in `i18n/request.ts`; whether `i18n-check` accepts split files is UNCONFIRMED and would be proven first. |
| `apps/web/e2e/screens.ts`                                                                                   | S0 splits it              | One screen list per area.                                                                                                                                                                                                                                                                                    |
| `apps/api/src/testing/**`                                                                                   | T1                        | Requests only.                                                                                                                                                                                                                                                                                               |

9. **Optional: one git worktree per slice** for a slice with long database tests. It isolates files and test runs, at the price of another install on a machine short of disk; the committer then merges in dependency order. The default is the shared tree with the rules above.

## 16. Tests and acceptance

The **money safety suite** must pass before any real money moves. `[proposal]`

1. Property tests over the in-memory ledger and the `decideAfterCheck` function (S2, S5a).
2. Concurrency tests on PostgreSQL: the slot race, double submit, release against reversal, fund against withdrawal, a retry storm, opposite transfers (S1, S2, S4, S5b).
3. Crash injection: abort a transaction after the state write and before the ledger write, and the reverse; nothing is persisted either way.
4. A long seeded scenario: a thousand tasks with random outcomes and the manual clock; after it, the reconciliation job finds I-1 to I-7 intact (O1).
5. End-to-end flows through the API and the web app with the fake world (T1).

Acceptance for the first pilot (follow and like tasks, manual credit):

1. An advertiser funds a campaign; a performer reserves, follows and submits; the reward shows as pending, then as released after the hold (manual clock).
2. An unfollow during the hold reverses it: the reward never reaches the wallet, the slot opens again and the escrow is whole.
3. No path in the safety suite double-pays or drives a balance negative.
4. A `source_error`, an `inconclusive` read or a `private` answer never reverses a hold or records a strike.
5. For several holds of one performer the verifier receives one call per kind in a window.
6. Every new screen passes axe with zero violations, stays under 150 KB gzip, and takes every string from the message file.
7. The reconciliation job is clean on the seeded scenario.

## 19. Self-review

Checks run against this plan before it was written down, each with what was found.

1. **A money path that can double-pay or go negative under concurrency.** Each flow in 7.2 was walked: every one is a compare-and-set on the owning object plus a ledger entry with a key derived from that object, in one transaction, and every debit lands on a tracked account with the nonnegative check. The races of 9.4 were enumerated. One gap was found and closed: the cancel refund `X` must be computed inside the transaction after locking the campaign row and its target rows `FOR UPDATE`, so a reservation cannot change `slots_taken` between computing `X` and shrinking `slots_total`; the order of 9.4 already requires it and 7.2 now says it.
2. **A state with no exit.** Every state of 6.1 to 6.5 was traced to a terminal state with no step that needs a person: reservations expire; holds are forced by the extension and outage caps; `cancelling` ends when its reservations and holds resolve; `paused` and `suspended` end at `ends_at`; a `requested` payout is inquired. A draft that is never funded costs nothing and may stay.
3. **A slice that secretly depends on another slice's files.** Three were found. S4 (completion creates the hold) and S5 (the engine acts on holds) formed a cycle; it is broken by splitting the pure hold domain into S5a, which S4 consumes. S3 and S4 both write `campaign_targets`; each now writes only its own column, and the database check ties them. S4 must change `social-accounts`; the change is named and assigned. The error codes, the message file, the ledger port, the migrations and the e2e world were also shared surfaces; each now has one owner (15.4).
4. **A contradiction with the verification rules.** A source error never becomes a negative: the decision function treats `source_error` and `inconclusive` as no information. A negative needs the chain's confirmation by a second source, and a reversal on `not_found` (`account_gone`) relies on `VERIFICATION_CONFIRM_NOT_FOUND`, which is on by default `[repo]`; with it off, `not_found` is treated as inconclusive. A `private` answer is final and costs no further source calls `[repo]`. The 30 s list cache only answers `verified`, never `not_following`, so it cannot reverse anything `[repo]`. Daily budgets are respected by the background share. One real hazard was found and designed around: a re-check capped at the default page count would read an honest performer as unfollowed (10.4).
5. **Marks.** Every external fact is in section 20 with its source; the ones that could not be confirmed are marked UNCONFIRMED where they are used.
